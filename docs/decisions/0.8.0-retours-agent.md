## Vérification de la piste 1 (2026-11-05)

- Le système de projet .NET a déjà un fournisseur, `StartupProjectSingleTargetGlobalBuildPropertyProvider`
  (Microsoft.VisualStudio.ProjectSystem.Managed.dll), qui passe `TargetFramework` = cible active.
  Il n'agit que si **toutes** ces conditions sont réunies (lu dans l'IL) :
  build implicite (F5/Ctrl+F5 : `QueryBuildManagerBusyEx() & 0xC0000`), projet = unique projet de
  démarrage, capacité `SingleTargetBuildForStartupProjects` (ajoutée par le SDK MAUI), option
  « préférer les builds à cible unique » activée.
- Mesuré sur une solution MAUI réelle : un Clean + Build (commande Générer) de l'application compile les deux
  cibles, Windows à 13:36:08 puis Android à 13:39:25 (+3 min). Son projet de tests, qui n'est pas
  projet de démarrage, compile toujours les deux.
- `IActiveDebugFrameworkServices` (public) : `GetProjectFrameworksAsync`,
  `GetActiveDebuggingFrameworkPropertyAsync`, `SetActiveDebuggingFrameworkPropertyAsync`.

## Prototype de la décision 1 (2026-11-05, instance expérimentale)

Solution de test : MultiApp (Exe, net8.0;net10.0, démarrage) → MultiLib (net8.0;net10.0) et
MonoLib (net8.0). Fichiers : `Vs/SingleTargetGlobalPropertiesProvider.cs`, `Vs/SingleTargetBuild.cs`.

| Essai | Résultat |
|---|---|
| `set_configuration(framework: net10.0)` puis `build` | MultiApp et MultiLib : net10.0 seul ; MonoLib : net8.0 |
| `build` sans réglage, pas de choix dans l'IDE | Cible active = première de la liste (net8.0) : net8.0 seul |
| `build` sans réglage, `ActiveDebugFramework = net10.0` | net10.0 seul |
| `framework: all` | toutes les cibles |
| `Build.BuildSolution` lancé hors MCP | toutes les cibles (fournisseur inactif) |

Pièges rencontrés :
- **Ordre des fournisseurs.** `TargetFrameworkGlobalBuildPropertyProvider` (Order 10) pose
  `TargetFramework=""` sur les configurations multi-cibles ; le plus grand ordre l'emporte. Le
  nôtre a `[Order(100)]`, sinon il est écrasé.
- **Lecture de la cible active.** `IActiveDebugFrameworkServices.GetActiveDebuggingFrameworkPropertyAsync`
  a renvoyé une chaîne vide ; la propriété évaluée `ActiveDebugFramework` (CPS,
  `GetCommonProperties().GetEvaluatedPropertyValueAsync`) est lue en premier.
- Un `.csproj.user` écrit hors de l'IDE n'est vu qu'après purge de `.vs/` (cache d'évaluation) ;
  sans incidence en usage réel, où c'est la liste déroulante qui l'écrit.
